## 1. Executive Summary

- **방향 평가 `[추정]`:** 평가→코칭 전환은 **제품적으로 타당**하다. 단순 정오 판정보다 "어디서 막혔는지·어떻게 고칠지"가 학생 가치가 크고, 성장·재작성 루프는 리텐션·재구매와 직결된다. **동의한다.**
- **독립 반론 `[확인됨]`:** 그러나 "전환 = 대규모 재개발"은 **틀렸다.** 코칭 데이터 모델·점진 힌트·재작성 성장 루프·무료 재첨삭 창은 **이미 구현**되어 있다(§0). 재개발이 아니라 **완성·연결·품질 개선**이 맞다.
- **실제 병목 3가지 `[확인됨]`/`[추정]`:** (1) 라이브 멀티모달 모델 미연결, (2) 모델 출력 콘텐츠 품질(코칭 깊이), (3) 시각 UX(렌더링·오버레이·음성).
- **아키텍처 권고(Q2) `[확인됨]`:** "평가 Worker 확장 vs 코칭 모듈 분리" 질문은 사실상 종결되어 있다. **이미 "코칭 모듈 분리"(MATH-5 학습 + MATH-6 재작성)가 MATH-4 평가 위에 올라간 구조**이며, "MATH-5는 수학적 정확성을 재계산하지 않는다"가 코드 주석으로 못 박혀 있다(`math-learning/types.ts` 주석). → **이 분리 구조를 유지·강화**하라. 새 파이프라인(C) 불필요.
- **이미지 직접분석(Q3) `[추정]`:** 추출은 이미 멀티모달이므로 "필수"는 아니지만, **난문항·손글씨에서 가치가 크다.** 단, 평가 입력에 원본 이미지를 더하려면 grounding/핀 계약을 보강해야 한다(§4). 단계적 도입 권고.
- **수학검증(Q4) `[추정]`:** 선행 보고서에서 밝힌 INVALID_OUTPUT 유력 원인(대안 동치 불확실 하드거부, `physical-contract.ts:56`)을 **SymPy 동치검증**이 근본 완화한다. 또한 "공식 해설과 다르다는 이유만의 오답"을 막는다(Owner §6 요구와 일치). **중간 수준(B+C: 공식해설 비교 + SymPy)** 권고, Wolfram은 선택.
- **무료 베타(Q7) `[추정]`:** 라이브 연결·콘텐츠 품질·PoC가 선행되어야 하므로 **"지금 당장"은 위험.** 전략 A(라이브 연결+품질)와 §11 PoC 통과 후 **무료 코칭 베타**를 여는 것이 현실적. 1 Credit 계약은 건드리지 않는 무차감 정책으로 설계 가능(§10).
- **인문 일정 영향 최소화(Q9) `[확인됨 구조]`:** Essay/Math 경로가 코드상 분리(`essay-runtime` vs `math-*`)되어 **인문 선출시를 막지 않는다.** 수리 코칭은 병행 개발·베타로 리스크를 흡수.

## 2. 현재 첨삭 결과의 문제 — 진단

Owner 관찰(문제1·3 "정답·풀이 타당", 문제2 "일부 오류 지적")과 "구체적 코칭 부족"은 **코드로 설명 가능**하다.

- **`[추정]` 원인은 데이터 모델이 아니라 출력 채움(populate) 품질이다.** CORE는 `title/diagnosis/why/next_action` 4필드를 가진 완전한 코칭 단위인데(`math-learning/core.ts:11`), 모델이 이를 "적절합니다" 수준으로 얕게 채우면 코칭이 빈약해진다. **CORE는 비어 있어도 유효**(`types.ts` 주석 "CORE may be empty")라서, 완성형 모범답안에는 CORE가 거의 안 생겨 "칭찬만 반복"되는 현상이 자연스럽게 나온다 — 이는 **모범답안을 넣었기 때문**이지 시스템 결함이 아니다.
- **`[확인됨]` 완성형 답안은 코칭이 적게 나오는 게 정상이다.** Owner가 넣은 것은 "공식 모범답안 수준의 완성형". 오류·막힘이 없으니 CORE/힌트가 적게 생성된다. **실제 학생(§2의 A~F 유형: 부분풀이·중단·계산오류·개념오류·근거생략·미접근)**에서야 코칭 모델이 제 값을 한다. → PoC는 반드시 **불완전 답안**으로 해야 한다(§11, Owner와 동일 결론).
- **`[추정]` 문제2 "미분가능성 오류 지적"의 신뢰성**은 선행 보고서의 (c)/(d) 리스크와 연결 — 모델이 실제로 없는 오류를 만들거나(§11 환각 검증 대상), 대안경로를 오답 처리할 수 있다. SymPy 검증이 방어선(§6).

**결론 `[추정]`:** 지금 결과가 얕은 이유는 (1) 입력이 모범답안이라 코칭할 게 적고, (2) 라이브 모델/프롬프트가 CORE·힌트를 깊게 채우도록 튜닝되지 않았기 때문. **데이터 모델 교체는 불필요.**

## 4. 이미지 기반 풀이 코칭 (하이브리드)

- **`[확인됨]` 추출은 이미 하이브리드 전단계를 갖춘다:** 원본 이미지 → 비전추출(`rawText`+`normalizedMath(LaTeX)`) → 임계영역 폴백 → 병합 → **학생확인 게이트**(불확실 시 학생에게 확인, `orchestration.ts:129-263`). Owner의 "불확실 부분 학생 확인" 요구는 **이미 구현**(NEEDS_CONFIRMATION).
- **`[확인됨]` 다중 이미지 순서 보존:** `pageIndex`+`readingOrder` 정렬(`orchestration.ts:152`), `MULTIPAGE_READING_ORDER`/`SUBPROBLEM_MARKERS` 벤치 카테고리 존재.
- **`[확인됨]` AI 인식 ↔ 원본 일치 확인 방법은 이미 두 겹:** (1) 1차·폴백 **이중 판독 일치 시 HIGH 승급, 불일치 시 학생확인/휴먼리뷰**(`orchestration.ts:198-221`), (2) 평가 스텝은 **핀 된 추출 영역만 인용 가능**(`UNGROUNDED_STEP_REGION`, `validation.ts:103`) → AI가 없는 영역을 지어내면 거부.
- **`[추정]` 원본 이미지 직접 분석(평가 단계 멀티모달)의 가치:** 손글씨·도형·그래프 배치가 평가에 중요할 때, 추출 텍스트만으로는 손실. 평가 LLM에 **원본 이미지 + 추출 grounding + 공식 문제/해설/기준**을 함께 주면 보정 가능. 단, 결과 스텝이 여전히 추출 영역에 매핑돼야 계약 만족(핀 유지).
- **권고 `[추정]`:** 이미지 직접분석은 **"필수"가 아니라 "난문항 선택 승급"** — 기본은 현 하이브리드, 추출 confidence가 낮거나 FULL_SOLUTION/PROOF일 때만 원본 이미지를 평가에 투입(비용 통제).

## 5. 이미지 렌더링과 시각적 첨삭

## 6. 수학적 정확성 검증

| 방식 | 정확성 | 비용 | 처리시간 | 개발난이도 | 비고 |
|---|---|---|---|---|---|
| A. 멀티모달 LLM 단독 | 중 | 저 | 빠름 | 낮음 | 환각·동치오판 위험 |
| B. LLM + 공식 해설 비교 | 중상 | 저 | 빠름 | 낮음(핀 이미 존재) | 공식 해설과 **다름≠오답** 처리 필요 |
| C. LLM + SymPy 검증 | **상** | 저(자체호스팅≈0) | 중 | 중 | 동치·수치대입 자동판정 |
| D. 단계별 풀이 검증 파이프라인 | 최상 | 중 | 느림 | 높음 | 스텝별 CAS 검증, 과함 |

- **`[확인됨]` SymPy가 푸는 실제 문제:** 선행 보고서에서 INVALID_OUTPUT 유력 원인이 **`MATHEMATICAL_EQUIVALENCE_UNCERTAIN` 경로의 물리단계 하드거부**(`physical-contract.ts:56`)였다. SymPy `simplify/equals`·수치 대입으로 **동치를 판정→완결**로 바꾸면 이 실패가 근본 완화되고, 동시에 "공식 해설과 달라서 오답" 문제(Owner §6)를 방지.
- **동치 불확실 처리 `[추정]`:** SymPy가 동치로 확정 → 대안경로 인정. SymPy도 불확실(초월방정식 등) → **오답 아님, `NEEDS_HUMAN_REVIEW`로 완결**(이미 유효 상태로 finalize됨, `worker-client.ts:77`). 즉 "애매하면 오답" 대신 "애매하면 사람 검토"로 안전 처리.
- **권고 `[추정]`: B+C(공식해설 비교 + SymPy).** D(스텝별 전면 CAS)는 비용·난이도 대비 과함. Wolfram은 라이선스·외부비용(`[검증필요]`)이라 후순위.

## 13. 최종 권고안 — 9개 질문 답변

**Q1. 평가 → 풀이 코칭 전환이 적절한가?**
`[추정]` **적절하다. 단, "전환"이 아니라 "이미 있는 코칭 레이어의 완성".** 제품 가치·리텐션 측면에서 옳고, 기술적으로는 재개발이 아니라 라이브 연결+품질+UX 문제(§0).

**Q2. Math Worker 확장 vs 코칭 모듈 분리?**
`[확인됨]` **코칭 모듈 분리(B)가 이미 현 아키텍처다. 그대로 유지·강화하라.** MATH-5/6가 MATH-4 위에 분리되어 있고 정확성 재계산을 하지 않음. 확장(A)·신규 파이프라인(C)은 불필요.

**Q3. 원본 이미지 직접 분석은 필수인가?**
`[추정]` **필수는 아니다(추출이 이미 멀티모달).** 다만 손글씨·도형·난문항에서 가치가 커, **조건부(저confidence·FULL_SOLUTION/PROOF) 승급**으로 도입 권고. grounding/핀 계약 보강 전제.

**Q4. 수학 검증은 어느 수준까지?**
`[추정]` **B+C 수준(공식해설 비교 + SymPy 동치검증).** INVALID_OUTPUT 근본 완화 + "다름≠오답" 방지. 스텝별 전면 CAS(D)·Wolfram은 과함/후순위.

**Q5. 수정 풀이를 이미지·수식으로 보여주는 방식은 현실적인가?**
`[추정]` **현실적이다.** 데이터(LaTeX·boundingBox·generated_solution·토글 UI) 이미 존재. KaTeX 렌더 + grounding된 영역만 오버레이 + 접힘 토글. 위치 못 특정 시 비표시는 코드로 안전(§5).

**Q6. 단계별 힌트와 재작성을 어떻게 연결?**
`[확인됨]` **이미 연결되어 있다.** L0(제공)→L1(SAFE_DIRECTION)→L2(CONCEPT_REVEAL)→해설, 그리고 `buildMath6Handoff`가 노출 힌트/해설공개 상태를 재작성 루프로 넘김(`handoff.ts`). CTA "답안을 다시 작성해 보세요" + 14일 무차감 창. **품질(힌트 body)만 올리면 됨.**

**Q7. 무료 베타는 언제 시작?**
`[추정]` **라이브 연결 + 콘텐츠 품질 + §11 PoC 통과 후.** 지금 당장은 위험(원인 미확정·모델 미연결). 1 Credit 불변·무차감 플래그로 정산 충돌 없이 운영 가능.
