## 2. 두 화면 UX 문제점 (화면 + CODE)

**인기 시험·학습자료 분석(A):** ① 6 KPI가 성격(입시/자료/학습) 미구분 ② 자료명 과장(한 줄에 "[2025년 11월 시행] 2026학년도 수능 기출 - 문제,답,해설…국어/영어/…") ③ 순위표 숫자 가독성 낮음(고유학생/기록수 두 열이 거의 동일값이라 의미 전달 약함) ④ 저장 vs 열람 차이 불명확 ⑤ **열람 쌍을 조회수로 오해 소지**(이미 "페이지뷰 아님" 주석 있음 — 시각화 필요).

**학습·입시 종합 현황(B):** ① 학습자료 이용(저장/열람)과 입시 지표가 **분리** ② **시간적 추이 없음**(스냅샷만) ③ 희망↔실제 지원 **관계 미표시** ④ 학생수 vs 기록수 구분은 표에 있으나 KPI엔 혼재 ⑤ 학습 성과 추적 부재 ⑥ Student 360 연결 제한(저장/열람·희망 미연계).

**공통:** 종합 현황은 KPI·순위·막대가 정돈된 반면 **인기 자료 화면은 텍스트·테이블 중심** → 디자인 시스템 불일치(§13 통일).

## 3. 공통 데이터·지표 정의 — 학생 수 ≠ 기록 수 (핵심)

- **고유 학생 수**: distinct user. **기록 수**: 행 수. 둘은 다르며 **대학별 학생 수 합계 ≠ 전체 고유 학생**(한 학생이 복수 대학 희망·지원 가능). 화면 순위표는 이미 `users`/`records` 2열 제공(CODE: `admin_learning_rankings_page` rows `{users,records}`). KPI에도 **단위 라벨 명시**(명 vs 건).
- **희망 대학**: 대학×학년도당 1건 → 학생수=기록수(화면 주석과 일치). **실제 지원**: 복수 전형·학과 가능 → 학생수<기록수.

## 5. 인기 시험·학습자료 분석 개편안 (A)

**A. KPI 재구성(성격 그룹)**: [입시 관심] 희망 대학 등록 학생·실제 지원 등록 / [자료 이용] 저장 기록·열람 쌍·(가능 시)고유 이용 학생 / [학습 활동] 공부시간·학습 기록 학생. → 성격별 3블록·단위 라벨.
**B. 인기 자료**: 저장 TOP 10 / 열람 TOP 10 **분리 탭**(현재 saved/recent 순위 재사용 A). 자료명 **말줄임 + [시행연도·시험] 칩 요약**, 전체는 title(hover). 재사용 A.
**C. 시험별 분석(시행연도/유형/학년/자료유형)**: **구조화 필드 존재 확인 필요** — 순위 RPC는 `content_items.title`만 반환. `content_items`에 exam_year/exam_type/grade/material_type 컬럼이 있으면 **C(최소 확장)**, 없으면 **제목 문자열 추론 금지(F)**. → §15 선확인.
**D. 검색·필터**: 기간(기존)·자료명 검색(기존) 우선. 시험유형/학년/자료종류는 C 확인 후. **기존 페이지네이션·전체 검색 유지**.
**E. 상세 이동**: 자료 순위 → 관련 자료/회원 상세. 기존 유지.

## 6. 학습·입시 종합 현황 개편안 (B) — 권장 IA

핵심 요약 + 상세 분리. 모든 지표를 한 화면에 노출하지 않음.
```
[기간] 핵심 KPI(활동학생·공부시간·저장학생·열람학생·희망등록·지원입력) ← 단위 명시
├ 학습 활동   공부시간 · 자료 저장 · 자료 열람 · 학습기록 학생 · (기간별 추이 D/E)
├ 학습 지속성 활동일·재방문·반복열람·저장후재열람  ← 전부 E(미수집) "수집 필요" 뱃지
├ 희망 대학·전공  등록학생·기록·평균희망·대학별 관심·전공별 관심 (A, 화면대로)
├ 실제 지원   지원학생·기록·대학별·전형별 (A) + [희망↔지원 관계 B]
├ 입시 결과   1단계/최종 합격·불합격·등록/미등록·미입력 (A, 표본 적을 때 해석 자제)
└ 학생별 상세 → Student 360 (복제 아님, 링크)
```
- **자료 이용 연결(현 문제1):** 종합 현황에 저장/열람 요약 삽입(materials-data와 동일 RPC 재사용, B).
- **희망↔지원 관계:** 같은 대학의 희망 학생 ∩ 지원 학생 교차 = **B(두 응답 조합)** 또는 D(정밀). 모집단 분리 유지.
- **기간별 추이:** 시계열 테이블 없음 → 윈도우 복수 호출 **B 조합**(월별), 정밀 추이는 D. 성적 추이는 **F**.

## 7. 희망 대학·전공 정의 / 8. 실제 지원·합격 정의
- 희망: 등록 학생수·기록수·학생당 평균·대학별 관심·대학별 1지망(지망순위 데이터 있을 때만)·전공별 관심. **희망 대학 모집단 ≠ 희망 전공 모집단**(별도 입력), **변경 이력 미저장 → 변경 추이 생성 금지**. 전부 A(화면 구현됨).
- 지원: 지원 학생수·기록수·대학별·전형별·1단계/최종 합격·합격 학생수·불합격·미입력. **학생수≠건수**(복수 전형). **결과 미입력 ≠ 불합격**. **자기보고 ≠ 검증 합격**(혼합 금지, 화면 주석과 일치). 합격률은 분모·분자 명확할 때만(화면 "집계 전" 유지). 표본 소수 → 과대 해석 금지. 전부 A/DONE.

## 9. 학습 활동 vs 학습 성과 (이번 개편 핵심)
- **활동**(공부시간·저장·열람·지속성·반복·논술이용): 일부 DONE(공부/저장/열람), 지속성·반복=E.
- **성과**(성적·성적변화·실제지원·입시결과·논술 평가결과): 성적=**F**(academic_performance null, `/admin/data/scores` NOT_IMPLEMENTED), 지원·입시결과=A, 논술 평가결과=DONE(/ql·essay).
- **원칙:** 활동 증가 → 성적 향상 **단정 금지**. 성적 데이터 없으면 **성적 향상 그래프 생성 금지**. 실제 데이터 있는 지표(지원·입시결과·논술)부터 학생별 추이.

## 11. 앱 이벤트 수집 현황 (조사 결과) — 핵심 사실
| 단계 | 상태 | 근거 |
|---|---|---|
| A Flutter 이벤트 발생(화면/메뉴/검색/PDF/저장/타이머/논술) | **NOT IMPLEMENTED/미확인** | WEB `ga4.ts`만 `page_view` 전송(클라이언트). 앱 내 메뉴·화면 이벤트 테이블 없음 |
| B 전송(GA4/Postgres) | WEB page_view→**GA4만**, Postgres 이벤트 **없음** | `ga4.ts`, 이벤트 ingestion RPC/테이블 미발견 |
| C 저장(이벤트 테이블) | **없음** | `recent_views`=projection(클릭 로그 아님, CODE 주석) |
| D 집계(조회수/메뉴클릭/기능) | **미수집** | 화면 "앱 메뉴 이용 TOP 3 = 집계 준비 중·미수집"(하드코딩) |
| E 관리자 조회 | GA4 리포트(visitors/installs)만 | `ga4-report.tsx` |
> **결론:** 과거 "31개 이벤트·14속성 정의"가 있어도 **실제 수집은 미완(앱 메뉴·화면·기능 이용은 Postgres에 없음)**. GA4는 **WEB 페이지뷰·방문/설치**만 커버. **앱 화면 조회 ≠ WEB 페이지 조회**. 저장(bookmarks)·열람(recent_views)·공부(study)·논술만 Postgres 보유.

## 12. 앱 이용 분석 설계 (전제: 이벤트 수집 먼저)
- 인기 화면·메뉴·기능·플랫폼·사용자 흐름 = **전부 E(이벤트 수집부터)**. 설계는 목표만: Flutter에서 `app_usage_events`(user·platform·screen/menu/feature·ts) 수집 → Postgres 집계 RPC → 관리자 순위. **이번 단계는 수집 체계 신설 금지**(조사·설계만). **중복 이벤트 체계 설계 금지**(기존 GA4·bookmarks·recent_views 우선).

### 15. 신규 집계·이벤트 필요 여부

- **D(신규 집계):** 희망↔지원 교차·정밀 기간 추이(필요 시).
- **E(이벤트 수집부터):** 앱 메뉴·화면·기능 이용, 재열람·저장후열람·학습 지속성. — **파이프라인 신설(후속 P2)**.

- **성능:** 페이지네이션 결과를 전체 집계로 쓰지 않음. 전체 고유 학생수 등은 **서버 집계(C)**로(클라이언트 전수 스캔 금지). 무거운 전체 스캔 지양, Supabase 안정성 고려.
